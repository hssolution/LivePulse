◎ 한 줄 요약

"라이브 시작" 버튼으로 들어간 화면이 좌장 화면인지 헷갈리고, 세션이 어떤 순서로 진행되는지 상상이 안 된다"는 문제의 근본 원인은 세 가지입니다. 각 문제에 대응하는 처방을 함께 제시합니다.

문제 1 · "좌장" 역할이 코드에 없다

DB에는 session_presenters(강연자)·session_partners(협업)만 존재. /console은 사실 파트너 콘솔인데 좌장 업무를 다 하므로 정체가 모호.

문제 2 · 운영 화면이 4개로 쪼개짐

/console · /presenter · /speaker · /broadcast. 이 중 /console↔/presenter는 기능이 거의 중복인데 "좌장 선택" 버튼이 중복 화면을 새 탭으로 엶.

문제 3 · 진행 단계가 화면에 안 보임

상태는 draft→published→active→ended 5개뿐. 라이브 중 세부 단계(대기/강연/Q&A/설문)는 broadcast_mode 속에 숨어 "지금 어디/다음 뭐"가 안 보임.

처방 1 · 콘솔 = 좌장 콕핏으로 재정의

"좌장 = 콕핏을 여는 사람"으로 정의. 새 DB 역할 신설 없이 운영 권한(owner/협업/confirmed presenter)으로 처리.

처방 2 · 중복 흡수 → 1콕핏 + 2보조

/presenter 고유 기능을 콕핏 우측 패널로 흡수. 운영 화면을 좌장 콕핏 · 강연자 · 송출 3개로 축소.

처방 3 · 단계 가시화 + 세부 단계 제안

콕핏 상단에 "지금 단계 · 다음 할 일" 상태 바 추가. 리허설·휴식 등 운영 단계를 제안 수준으로 확장.

1 현황 진단 (As-Is)

지금 코드가 실제로 어떻게 생겼는지부터 정리합니다.

1-1. 역할 혼란 — "말"과 "코드 실체"의 불일치

UI/문서에 등장하는 말코드/DB의 실체결과
좌장 (콘솔 "좌장 선택" 버튼, StageControl 주석 "좌장/콘솔 공용")독립 역할/테이블 없음. session_members.role에 moderator enum은 있으나 실사용 제한적좌장이 누구인지·어느 화면인지 불명확
행사주최자 / 파트너partners + sessions.partner_id콘솔의 실제 소유자. 그러나 화면명이 "콘솔"이라 좌장과 구분 안 됨
강연자 / 발표자session_presenters (member/partner/manual, status pending→confirmed)비교적 명확. /speaker 사용
협업 파트너session_partners (status accepted)준비·운영 공동 권한
관리자 보기 모드ViewAsBanner + PartnerContext캡쳐 상단 노란 배너가 이것
핵심: 캡쳐 화면(/partner/sessions/:id/console)은 "행사주최자(또는 위임받은 운영자)가 라이브를 진행하는 콘솔"입니다. 기능상 좌장이 할 일을 모두 하지만, 이름·정보구조가 그 사실을 드러내지 않아 헷갈립니다.

6 권장 조정 & 단계적 로드맵

충격을 최소화하도록 3단계로 나눕니다. P1~P2는 프론트 중심, P3는 DB 영향이 있어 별도 결정·적용이 필요합니다.

P1 · 용어 & 정보구조 정리 코드 소폭

console을 화면·문구상 "좌장 콕핏"으로 라벨링. 상단에 "지금 단계 · 다음 할 일" 상태 바 추가(현재 status + broadcast_mode를 사람이 읽는 한 줄로 표현). 헤더의 "좌장 선택" 버튼 제거 검토.

영향: src/pages/partner/SessionConsole.jsx, src/components/session/StageControl.jsx

P2 · 중복 흡수 리팩터

/presenter의 고유 기능(질문 즉시 선택·강연자 지정)을 콕핏 우측 패널로 이관. /presenter 라우트는 콕핏으로 리다이렉트하거나 모바일 보조 뷰로 격하. 권한 판별 로직(PresenterQnA.jsx 44–107행)을 콕핏 진입 가드로 재사용.

영향: SessionConsole.jsx, ManagerQnA.jsx, PresenterQnA.jsx, src/App.jsx(라우팅)

P3 · 상태 모델 확장 DB 영향 · 사용자 결정

리허설/대기실 · 휴식 단계 도입. 두 가지 구현 옵션을 검토 후 선택:

옵션방식장점단점
Asessions.status에 ready 추가일생 단계가 명확, 리포트·통계 분리 쉬움상태 enum·프로시저 다수 수정
Bactive 유지 + stage_phase 컬럼/플래그기존 상태 흐름 유지, 변경 국소적"라이브 안의 단계" 개념이 한 겹 더

※ 휴식(intermission)은 옵션 B 성격(active 내부 모드)이 자연스럽고, 리허설은 옵션 A/B 모두 가능합니다.

영향: supabase/migrations/*, sp_partner_session_status_s 등 프로시저, StageControl.jsx, LiveSession.jsx, BroadcastQnA.jsx · SQL 적용은 사용자가 직접(프로시저 배포 모델 준수)
